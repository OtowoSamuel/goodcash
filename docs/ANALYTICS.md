# Analytics and Dune dashboard

## Scope

GoodCash analytics are wallet-level only. Wallet addresses are pseudonymous personal data under the NDPA 2023 and must be treated as personal data, not anonymous identifiers. We intentionally do not send bank details, names, phone numbers, or raw partner payloads to analytics systems.

The contract event `CashOut` is the source of truth for product volume. App-level events are used for funnel analysis only and should never mix in raw RPC payloads or partner responses.

## Event schema

### Contract event: `CashOut`

Canonical contract fields:

- `user` — wallet address of the swap caller
- `recipient` — output recipient wallet or off-ramp wallet address
- `tokenOut` — output token address
- `amountIn` — G$ amount input (raw uint256)
- `amountOut` — output amount (raw uint256)
- `route` — enum: `0 = reserve`, `1 = uniswap`
- `ref` — app-generated bytes32 reference

### App events

| Event | Source | Payload | Notes |
| --- | --- | --- | --- |
| `wallet_connected` | app | `wallet`, `wallet_type`, `referral_tag` | No names or phone numbers |
| `balance_viewed` | app | `balance_bucket` | Bucketed, not full value |
| `readiness_viewed` | app | `balance_bucket`, `days_to_minimum_bucket`, `state` | Bucketed only |
| `quote_shown` | app | `amount`, `route`, `price_impact`, `exit_contribution`, `swap_fee`, `estimated_naira` | `estimated_naira` is the modeled value, not a bank or account field |
| `swap_submitted` | app | `amount`, `slippage_setting`, `route` | Track conversion attempts |
| `swap_failed` | app | `reason_code` | Standardized slippage / pause / RPC / gas reasons |
| `claim_confirmed` | on-chain | `wallet`, `amount` | Wallet is the subject; no PII |
| `handoff_clicked` | app | `partner` | Only the partner name |
| `order_created` / `order_paid` / `order_settled` | app/backend | `partner`, `amount_bucket`, `status` | No bank details |
| `goal_created` / `alert_created` | app | `goal_bucket`, `alert_type` | Bucketed only |
| `weekly_return` | derived | `wallet` | Derived from wallet-level weekly activity |

## Client instrumentation

The web app emits events through `apps/web/src/lib/analytics.ts` with a dedupe guard so a single user action is recorded once. The module strips disallowed keys (`name`, `phone`, `bank`, `account_number`, etc.) before batching or sending.

## Retention and governance

- Raw app events retained for 90 days in a privacy-friendly analytics store.
- Aggregated wallet-level metrics retained for 18 months for product and compliance analysis.
- Banks, personal names, phone numbers, direct partner payloads, and raw RPC payloads are never stored in analytics.
- Wallet addresses remain pseudonymous and are used only at the wallet-level for cohorting, retention, and conversion analysis.

## Dune query spec

Use the canonical `CashOut` contract event table and a price table keyed by block time (or the Reserve quote at the time of the swap) to compute USD value at swap time.

### 1) Cumulative and weekly G$ routed + USD value

```sql
WITH cashout AS (
  SELECT
    evt_block_time AS ts,
    evt_block_number AS block_number,
    user,
    recipient,
    amountIn,
    amountOut,
    CAST(route AS INT) AS route,
    ref,
    CAST(amountIn AS DOUBLE) / 1e18 AS g_routed,
    CAST(amountOut AS DOUBLE) / 1e6 AS usdt_out
  FROM goodcash.CashOut
),
priced AS (
  SELECT
    c.ts,
    c.user,
    c.g_routed,
    c.usdt_out,
    p.price_usd,
    c.g_routed * p.price_usd AS usd_value_at_swap_time,
    c.route
  FROM cashout c
  LEFT JOIN dune.price_tables.celo_usd p
    ON DATE_TRUNC('minute', c.ts) = DATE_TRUNC('minute', p.ts)
)
SELECT
  DATE_TRUNC('week', ts) AS week_start,
  SUM(g_routed) AS g_routed_weekly,
  SUM(usd_value_at_swap_time) AS usd_value_weekly,
  COUNT(*) AS swaps,
  COUNT(DISTINCT user) AS unique_wallets
FROM priced
GROUP BY 1
ORDER BY 1 DESC;
```

The cumulative version is the same query without the weekly grouping, using a running total window over `ts`:

```sql
SELECT
  ts,
  SUM(g_routed) OVER (ORDER BY ts) AS cumulative_g_routed,
  SUM(usd_value_at_swap_time) OVER (ORDER BY ts) AS cumulative_usd_routed
FROM priced
ORDER BY ts;
```

### 2) Unique wallets, new vs returning, and route split

```sql
WITH cashout AS (
  SELECT
    user,
    MIN(ts) AS first_seen,
    COUNT(*) AS swaps,
    SUM(g_routed) AS g_routed,
    MAX(CASE WHEN route = 0 THEN 1 ELSE 0 END) AS via_reserve,
    MAX(CASE WHEN route = 1 THEN 1 ELSE 0 END) AS via_uniswap
  FROM priced
  GROUP BY user
)
SELECT
  COUNT(*) AS total_wallets,
  COUNT(CASE WHEN first_seen >= DATE_TRUNC('week', CURRENT_DATE) THEN 1 END) AS new_wallets_this_week,
  COUNT(CASE WHEN first_seen < DATE_TRUNC('week', CURRENT_DATE) THEN 1 END) AS returning_wallets,
  SUM(via_reserve) AS reserve_swaps,
  SUM(via_uniswap) AS uniswap_swaps,
  SUM(g_routed) AS total_g_routed
FROM cashout;
```

### 3) Median swap size and median cost percent

```sql
WITH cashout AS (
  SELECT
    user,
    ts,
    g_routed,
    usd_value_at_swap_time,
    CASE
      WHEN route = 0 THEN 0.10
      ELSE 0.00
    END AS exit_contribution,
    100 * (1 - (usd_value_at_swap_time / NULLIF(g_routed * 0.00011399, 0))) AS cost_percent
  FROM priced
)
SELECT
  PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY g_routed) AS median_swap_size_g,
  PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY cost_percent) AS median_cost_percent
FROM cashout;
```

### 4) Cash-out completion rate

```sql
WITH events AS (
  SELECT
    partner,
    DATE_TRUNC('day', ts) AS day,
    COUNT(CASE WHEN event_name = 'order_created' THEN 1 END) AS orders_created,
    COUNT(CASE WHEN event_name = 'order_settled' THEN 1 END) AS orders_settled
  FROM goodcash.app_events
  WHERE event_name IN ('order_created', 'order_settled')
  GROUP BY 1, 2
)
SELECT
  SUM(orders_created) AS total_created,
  SUM(orders_settled) AS total_settled,
  100.0 * SUM(orders_settled) / NULLIF(SUM(orders_created), 0) AS cashout_completion_rate_pct
FROM events;
```

## Security and privacy notes

- Never send raw RPC payloads, partner responses, or personal bank data to analytics.
- Route split and conversion metrics are derived from contract events and wallet-level app events only.
- Wallet addresses are pseudonymous personal data. Treat them as customer-level identifiers under the project privacy notice, not as anonymous user IDs.
